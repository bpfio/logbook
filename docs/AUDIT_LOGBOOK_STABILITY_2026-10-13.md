## 一、执行摘要

据 `docs/DEVLOG.md` 的历史记录，Logbook 的既有数据卷生产路径曾能运行；本次仅审查本地代码，未实机复验 QNAP。代码层面的稳定性问题集中在三个层面：

1. **安装与迁移不可复现**：干净 PostgreSQL 卷无法获得完整 Schema，已有数据卷会掩盖问题。
2. **并发原语不成立**：连接池初始化存在竞态，文件租约不是原子互斥，普通任务读写仍反复执行 DDL。
3. **故障缓解依赖猜测**：SSH 的 300ms 缓冲只能缩短取消窗口，不能覆盖慢调用；信箱读取又缺少收件人鉴权。

因此，近期“测试全绿、生产内存正常”不足以证明系统稳定。当前最需要修复的不是功能数量，而是首次安装、并发正确性和干净环境门禁。

## 二、审计范围与方法

本次审计覆盖：

- `docs/DEVLOG.md`、`AGENTS.md` 与当前 Git 工作区状态；
- `src/logbook/db.py`、`mcp_server.py`、`ssh_server.py`；
- PostgreSQL 初始化与迁移脚本、本地及 QNAP Compose 配置；
- `tests/`、`scripts/gate.sh`、依赖锁与部署文档；
- 全量测试、无数据库测试、源码编译检查和连接池并发探针。

本次未启动或修改 PostgreSQL、SSH 服务及生产环境，因此不包含真实数据库并发压测和生产网络渗透测试。

## 三、发现汇总

| ID | 级别 | 领域 | 发现 | 主要影响 |
|---|---|---|---|---|
| A-01 | P0 | 初始化/迁移 | 干净数据库缺少完整 Schema 与迁移链 | 首次部署或恢复后核心读写失败 |
| A-02 | P1 | 并发/数据一致性 | 文件租约采用先查后写，无原子互斥 | 两个 Agent 可同时获得同一文件施工权 |

| A-04 | P1 | 性能/锁竞争 | 普通任务读写每次执行整套项目 DDL | 延迟抖动、锁竞争、10 秒超时风险 |
| A-05 | P1 | MCP/SSH 生命周期 | 输入 EOF 后仅固定等待 300ms | 调用超过 300ms 时仍可能被取消 |

## 四、详细发现

### A-01：干净环境无法完整初始化（P0）

**证据**

- 根 `docker-compose.yml` 仅挂载 `sql/01_init.sql`，没有执行 `02` 至 `07` 迁移。
- `sql/01_init.sql` 创建的任务表没有 `reviewer`、`agent_ip` 等后续字段，但 `Database.upsert_task()` 写入这些列。
- QNAP Compose 挂载的 `deploy/qnap/init.sql` 只有 `CREATE SCHEMA IF NOT EXISTS shared;`，没有共享表，也没有 `shared.init_project_schema()`。
- QNAP 部署文档只列出 `02`、`03`，未覆盖当前版本依赖的 `04` 至 `07`。

**触发路径**

1. 使用空目录建立新的 PostgreSQL 数据卷；
2. 按 README 或 QNAP Compose 启动；
3. 调用任务、项目或知识库工具；
4. 出现 `shared.init_project_schema()` 不存在、字段不存在或共享表不存在。

**影响**

已有生产卷会掩盖 Schema 缺口，因此日常热升级可能表现正常；灾备恢复、换机和全新部署则会失败，属于发布阻断问题。

**修复要求**

- 建立唯一的版本化迁移入口，并记录 `schema_migrations` 版本；
- 新卷按 `01` 至 `07` 自动执行，现有卷只执行缺失版本；
- 增加“空数据库 → 全量迁移 → MCP 冒烟 → 重复迁移”自动化测试；
- 修正 QNAP `init.sql` 与部署文档，禁止三套初始化文件继续分叉。

### A-02：文件租约不是原子互斥（P1）

**证据**

`Database.acquire_file_lease()` 先查询现有租约，再执行无条件 `ON CONFLICT ... DO UPDATE`。冲突更新不带 `lease_expires_at` 或原持有人条件，因此：

- 两个并发请求读取到“无租约”后都执行插入；
- 第二个请求冲突并覆盖第一个请求；
- 两个调用方都收到 `success=True`。

现有测试只覆盖模型、签名和单次调用，没有并发租约测试。

**影响**

该功能宣称防止多 Agent 写同一文件，但无法保证互斥，可能导致覆盖写、评审冲突和任务状态互相污染。

**修复要求**

- 在一个 PostgreSQL 事务中使用行锁、条件 upsert 或 advisory lock；
- 条件必须限定“租约已过期或仍由同一 Agent 持有”；
- 并发测试必须断言恰好一个成功、一个收到 `LEASE_CONFLICT`；
- 使用数据库时钟判断过期，避免应用与数据库时钟差异。

### A-03：连接池与 DDL 首检存在竞态（P1）

**证据**

`Database.connect()` 在 `await create_pool()` 完成前没有锁。三个并发首请求的探针结果为：

```text
create_pool_calls=3
stored_pool_is_last=True
leaked_pool_refs=2
```

消息和调研 Schema 的布尔标志也在 DDL 完成前可被多个协程同时观察为 `False`。

**影响**

启动高峰期会额外创建连接池、泄漏连接和触发 DDL 锁竞争，随后内存及 PostgreSQL 连接数可能缓慢上涨。

**修复要求**

- 为池初始化、关闭及事件循环切换建立明确的异步同步原语；
- DDL 使用单飞锁，只有成功后才发布就绪状态；
- 连接池异常时清理半初始化状态；
- 增加多协程同时首调用测试，断言只创建一个池、只执行一次 DDL。

### A-04：普通任务读写仍每次执行完整 DDL（P1）

**证据**

`ensure_project()` 每次都执行 `shared.init_project_schema($1)`；该函数会尝试创建 Schema、5 张表及 6 个索引。`db.py` 中共有 13 个调用点，覆盖任务、发现、待办、批次等主要读写路径。

**影响**

即使对象已经存在，每笔调用仍要解析并执行整套 DDL。高并发时会增加延迟抖动、锁等待和 `command_timeout=10` 超时概率；这也与近期信箱故障“重复 DDL 导致调用断连”的根因属于同类问题。

**修复要求**

- 每个进程每项目缓存 Schema 就绪状态；
- 常规读写前仅验证关键表和必要列，不重复 DDL；
- Schema 版本升级通过迁移显式完成；
- 用基准测试对比首调用、稳态调用和并发调用延迟。

### A-05：SSH 300ms 缓冲不是生命周期修复（P1）

**证据**

`pipe_streams()` 在输入 EOF 后固定等待 300ms，再向子进程写 EOF。任何超过 300ms 的数据库查询、向量 API、链式工具或慢网络调用仍会在 EOF 后被 MCP 引擎取消。

新增测试只验证信箱资源渲染和布尔字段初值，没有覆盖真实 stdin EOF、慢调用、取消恢复或响应完整回写。

**影响**

该方案能掩盖已优化后的 2ms 信箱写入，但不能根治 `-32000 Connection closed`；调用时长跨过阈值时故障会复现，短调用则无条件增加 300ms 延迟。

**修复要求**

- 不用固定时长猜测任务结束，应以 MCP 协议请求/响应生命周期驱动 EOF；
- 明确分离客户端 stdin EOF、服务端任务完成和 stdout 关闭；
- 对断连中的幂等写入提供请求 ID，客户端可安全查询或重试；
- 增加 1ms、500ms、5s 调用及连接中断的回归测试。

### A-06：信箱读取没有收件人鉴权（P1）

**证据**

`message_read()` 接收可选 `agent_name`，但 `read_agent_message()` 的 SQL 只按 `id` 更新，不使用该参数，也不返回收件人校验分支。

**影响**

任何知道或枚举全局自增 ID 的调用者可以读取其他 Agent 的信件，并将其永久标记为已读，造成信息泄露和待办状态丢失。

**修复要求**

- 必须显式提供操作者身份，并在 SQL 中限定 `to_agent = $agent`；
- 区分“不存在”和“无权访问”，避免枚举信件；
- 审计字段记录操作者，不能接受任意可选值后忽略；
- 增加跨 Agent 拒绝、本人读取成功、重复读取幂等测试。

### A-07：SSH 存在已知默认口令（P1）

**证据**

- `DEFAULT_PASSWORD = os.getenv("SSH_PASSWORD", "logbook")`；
- 密码认证始终开启；
- QNAP Compose 使用 `${SSH_PASSWORD:-logbook}`；
- 服务默认监听 `0.0.0.0:22`。

**影响**

生产环境只要漏配或留空 `SSH_PASSWORD`，就会接受公开代码中可预测的弱口令，并获得 MCP 与 CLI 权限。部署文档要求人工确认，但默认值会让错误配置静默成功。

**修复要求**

- 生产模式缺少强口令或授权公钥时启动失败；
- 删除 Compose 和代码中的口令默认值；
- 优先仅允许公钥认证，口令认证需显式开关；
- 增加启动配置校验和认证失败测试。

### A-08：质量门禁不可在干净环境复现（P2）

**证据**

- 全量测试收集 64 项，当前环境 34 项通过、30 项失败；失败根因为 PostgreSQL 未启动。
- `scripts/gate.sh` 直接运行 pytest、真实写入重放、brief 度量和去重查询，没有前置依赖检查。
- 部署测试读取被 `.gitignore` 排除的 `deploy/qnap/compose.yaml` 与 `.env`，这些文件不在 Git 中。
- 无数据库抽样测试 8/8 通过，源码 `compileall` 和 `git diff --check` 通过。

**影响**

当前机器上的“全绿”依赖开发者本地状态，CI、新成员和灾备环境无法复现；未入库的部署文件还会使测试在干净检出直接报错。

**修复要求**

- 用临时 PostgreSQL 容器提供隔离测试库并自动迁移；
- 将单元测试、数据库集成测试和生产重放分层；
- 部署测试读取 Git 跟踪的 example 文件，不读取本机 `.env`；
- 门禁开始时明确输出依赖检查结果，失败时给出可操作诊断。

## 五、修复优先级

### 第一波：发布阻断与正确性

1. 修复 A-01，完成全新数据库全链路迁移验证。
2. 修复 A-02，证明文件租约并发下严格互斥。
3. 修复 A-03，保证单进程只创建一个池、执行一次首检 DDL。
4. 修复 A-06，阻断跨 Agent 信件读取。

### 第二波：运行稳定性与安全

1. 修复 A-04，移除常规路径重复 DDL。
2. 修复 A-05，以协议生命周期替代 300ms 猜测。
3. 修复 A-07，移除默认弱口令并收紧 SSH 启动配置。

### 第三波：验证体系

1. 修复 A-08，建立可复现的临时数据库门禁。
2. 增加并发、干净部署、慢调用、断连恢复和迁移重放测试。
3. 修复全部 P0/P1 后再执行 QNAP 热升级和回滚演练。

## 六、验收标准

本轮稳定性整改只有同时满足以下条件才算闭环：

- 空数据库可从 `01` 自动迁移到当前版本，连续执行两次均成功；
- 新卷上 25 个 MCP 工具、8 个 Resources 和 4 个 Prompts 冒烟通过；
- 并发租约测试稳定满足“唯一成功者”，至少重复 100 次无异常；
- 三个并发首请求只创建 1 个连接池、执行 1 次 DDL 首检；
- 慢于 300ms 的 MCP 调用在 stdin EOF 条件下仍能完整收到响应；
- 非收件 Agent 读取信件稳定返回无权访问，且不改变已读状态；
- 缺少 SSH 强凭据时服务拒绝启动；
- 干净 Git 检出在无本地 `.env`、无本机 PostgreSQL 的情况下门禁通过；
- QNAP 升级前完成备份、升级后完成数据量对账，并验证旧镜像回滚路径。
